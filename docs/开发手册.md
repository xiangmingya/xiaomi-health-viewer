# 开发手册：小米运动健康云端日报查看

本文按“先运行 → 看懂数据 → 看懂代码 → 修改与排错”的顺序介绍项目。读者不需要了解小米接口逆向即可使用；修改代码时，应理解接口参数、时间单位和空数据语义。

## 1. 项目目标和数据链路

这个项目解决的问题是：在本机或青龙容器里，按需查看本人小米运动健康已经上传到云端的数据。

```text
手机/手环采集 → 手机小米运动健康 App 同步上传
                              ↓
                    小米运动健康云端
                              ↓
                  xiaomi_health.py 只读查询
                              ↓
                      中文摘要 / JSON
```

脚本不通过蓝牙读手环，不触发手机同步，不启动常驻服务。默认只有三个命令：登录、最新日报、历史日报。数据库、网页、定时同步和通知没有实现。

“最新日报”指近 7 天内各指标最新一条日报。步数和睡眠可能来自不同日期，所以每项各自显示日期。没有今日数据时不会把昨日的值改标成今天。

## 2. 环境与第一次运行

- Python 3.11+；本次实测使用 3.12。
- `mi-fitness==0.2.0`，该第三方 SDK 负责小米账号登录、请求签名、加解密和自动续期。
- 手机 App 登录与数据对应的小米账号，并已同步过数据。
- 能访问 `account.xiaomi.com` 及它提供的登录域名、`sts-hlth.io.mi.com`、`hlth.io.mi.com`。

完整安装步骤见[运行说明](运行说明.md)。开发者也按相同方式安装依赖；不要手工编辑或构造 token 文件。

```bash
python -m pip install -r requirements.txt
python xiaomi_health.py login --probe
python xiaomi_health.py latest
python xiaomi_health.py history --date 2026-10-11 --days 7 --json
```

## 4. 登录与凭据生命周期

### 4.1 扫码流程

`main()` 创建 `XiaomiAuth`，调用 `login_qr()`，用回调打印二维码图片链接和备用登录链接。用户在小米官方页面完成登录和确认，SDK 长轮询等待结果，随后完成服务令牌交换。

确认成功后，`auth.save_token()` 写入指定文件；脚本把文件权限设置为 `600`。登录流程最长等待约 300 秒。

`login` 只登录。`login --probe` 在保存凭据后，继续调用查询流程。若试读失败，已经保存的有效凭据仍可用于下次重试，不能把“查询失败”理解成“登录失败”。

### 4.2 后续查询

`MiHealthClient.from_token(path)` 加载凭据，脚本从 `client.auth.token.user_id` 取当前账号 UID。调用者不必提供 UID，且没有查询其他任意账号的命令参数。

SDK 收到认证失效时会尝试刷新并重试；刷新成功后可保存新凭据。只有刷新失败，才需要用户重新登录。脚本结束时分别关闭查询客户端和认证客户端。

### 4.3 路径和日志

`--token` 优先于 `MI_TOKEN_FILE`，两者都未指定时使用脚本旁的 `private/token.json`。默认路径不依赖当前工作目录；自行提供相对路径时则按终端工作目录解析。

脚本启动时设置 `umask(077)`，禁止 SDK 的默认日志输出，避免 SDK 记录认证细节。脚本只显示自己控制的提示和查询结果，错误不会直接打印响应体、完整请求 URL 或 token。

## 5. 为什么本人查询没有直接使用 SDK 的所有便利方法

SDK 文档主要面向亲友共享数据。亲友端点例如：

```text
/app/v1/relatives/get_aggregated_data
/app/v1/relatives/get_latest_data
/app/v1/relatives/get_fitness_data
```

本人端点的名称不同，不是只把 `relatives` 替换成 `data`：

```text
/app/v1/data/get_aggregated_fitness_data_by_time
/app/v1/data/get_latest_fitness_data
/app/v1/data/get_fitness_data_by_time
```

最初仅替换前缀的路径返回 HTTP 404。本人日报路径修正后，已成功取到真实账号的步数日报。

本人 `get_latest_fitness_data` 在本次测试中返回业务码 `-8`，不能当作已经打通的最新快照接口。当前脚本通过日报接口读取近 7 天数据，取每项最近一条；这比调用失败后静默返回空值更容易核对。

SDK 的 `get_latest_daily_summary()` 仍会寻找亲友；部分最新指标方法在数据缺失时还会查询共享权限。因此当前代码直接使用 SDK 的内部 `client._request()` 调本人日报路径，而不全面修改亲友模块。

**维护约束**：`_request()` 是内部方法，因此依赖固定为 0.2.0。升级 SDK 时，先检查签名、返回结构、自动续期行为和关闭客户端的方法，再做真实账号回归。

## 6. 当前使用的只读接口

### 6.1 请求

```text
GET https://hlth.io.mi.com/app/v1/data/get_aggregated_fitness_data_by_time
```

业务参数交给 SDK；SDK 将它们编码成紧凑 JSON，再签名、加密和发送。下表是**加密前的业务参数**，不是让你把它们直接拼接进普通 URL。

| 参数 | 类型 | 当前取值/用途 |
|---|---|---|
| `relative_uid` | 整数 | 从登录凭据取当前用户 UID；沿用实测可用的请求格式 |
| `key` | 字符串 | `steps`、`heart_rate`、`sleep`、`spo2` |
| `tag` | 字符串 | `daily_report` |
| `start_time` | 整数 | 查询首日北京时间 00:00:00，Unix 秒 |
| `end_time` | 整数 | 结束日 23:59:59，最多到当前时间，Unix 秒 |
| `limit` | 整数 | `max(days, 7)` |

**这份参数表只适用于本项目实测使用的日报请求格式。**其他小米端点可能使用不同字段、时间单位和 tag，不要把它照搬到分钟级数据或运动记录接口。

本次对比发现，另一个网上实现中的 `startTime/endTime` 毫秒格式配合 `daily_report` 返回了超出指定窗口的旧数据。因此代码除了发送实测参数，还会在本地按记录时间再次过滤，防止把越界数据当成查询结果。

### 6.2 返回结构

下面是**构造的示例**，不是仓库作者的真实健康数据：

```json
{
  "code": 0,
  "message": "success",
  "result": {
    "data_list": [
      {
        "key": "steps",
        "time": 1791648000,
        "value": "{\"steps\":5000,\"distance\":3000,\"calories\":200}"
      }
    ],
    "has_more": false
  }
}
```

`value` 可能是 JSON 字符串，也可能已经是字典。`daily_records()` 统一解析成字典，把外层记录的 `time` 加进去，再按时间排序。构造示例中的 `time` 只用于说明字段，不应拿来判断实际数据日期。

若 `has_more=true`，当前版本明确报错，不会把未读完的数据展示成完整日报。使用者可缩小时间窗口。自动翻页属于后续扩展，当前版本没有实现。

## 7. 日期窗口和时间单位

`--date` 是结束日期；未指定时使用北京时间今天。`--days=N` 包含结束日和之前 N−1 天。

例如：

```bash
python xiaomi_health.py history --date 2026-10-11 --days 7
```

窗口为北京时间 **2026-10-05 00:00:00 至 2026-10-11 23:59:59**。

- 全部日边界使用 `Asia/Shanghai`，不受青龙容器的 UTC 默认时区影响。
- 入参和日报记录的 `time` 在这条链路中都用秒。
- 如果结束日是今天，结束时间截断到实际当前时间，避免查询未来。
- 如果整个窗口都在未来，返回空列表，不访问云端接口。
- 本地还检查 `lower <= item.time <= upper`，丢弃超出窗口的记录。
- `queried_at` 是查询时间；日报 `time` 通常是数据所属日时间，不是上传时间。

`latest` 固定查询近 7 天，并取每个指标按 `time` 排序后的最后一条。近 7 天完全无记录的指标为 `null`；它不会自动搜索几年前的历史。

## 8. 指标字段与单位

| key | 中文摘要字段 | 单位/说明 |
|---|---|---|
| `steps` | `steps`、`distance`、`calories` | 步、米、千卡；这里是日报汇总 |
| `heart_rate` | `avg_hr`、`avg_rhr`、`min_hr`、`max_hr` | 次/分；`latest_hr` 可带最近采样值和时间 |
| `sleep` | `total_duration`、`sleep_score` | 总时长分钟；摘要换算成小时/分钟，评分单独展示 |
| `spo2` | `avg_spo2`、`min_spo2`、`max_spo2` | 百分比；`latest_spo2` 可带最近采样值和时间 |

完整字段以 `--json` 的实际返回值为准。云端旧记录的结构可能与新记录不同；当前中文展示面向这些已知字段，不对未识别字段进行猜测换算。

不要把分钟级原始步数 `value` 与日报累计混为一谈，也不要把睡眠日报日期直接视为入睡日期。需要分段入睡/醒来时间时应读取原始 `segment_details`，逐段解释其时间字段。

## 9. 输出协议和退出码

默认是面向人的中文摘要。外部系统接入时使用 `--json`，不要解析中文句子。

| 字段 | 含义 |
|---|---|
| `queried_at` | 带时区的查询时间 |
| `source` | 数据来源说明 |
| `mode` | `latest_daily` 或 `history` |
| `end_date` / `days` | 实际查询结束日和天数 |
| `steps` / `heart_rate` / `sleep` / `spo2` | 指标结果 |

指标结果有三种形态：

1. 成功有数据：`latest` 为字典，`history` 为字典列表。
2. 成功无数据：`latest` 为 `null`，`history` 为 `[]`。
3. 请求失败：字典中有 `error`、`status_code`、`code`；本地分页或数据结构错误还会有 `detail`。它与空数据不同。

`--json` 主要供 `latest/history` 查询输出使用；登录过程仍会显示登录提示和临时链接，不能把 `login --probe --json` 的整个 stdout 当作一个纯 JSON 文档。

退出码：全部查询成功为 `0`，包括成功但无数据；任一指标请求失败、未登录、登录失败为 `1`；非法参数通常为 `2`；用户取消为 `130`。四个指标逐项查询，一项失败后会继续尝试其他项，每项最多等待 45 秒，因此最慢可能累计等待约 180 秒。

## 10. 函数地图：从哪里开始改

| 函数 | 责任 | 常见修改点 |
|---|---|---|
| `arguments()` | 解析命令、日期、token 路径和 JSON 开关 | 增加 CLI 参数 |
| `main()` | 关闭 SDK 日志；登录；触发查询 | 调整登录提示 |
| `query()` | 加载凭据、依次查四个指标、控制超时和退出码 | 增加指标、调整时间上限 |
| `daily_records()` | 计算时间窗口、调用本人日报接口、解析和过滤 | 排查端点/字段变化 |
| `format_time()` | 统一按北京时间格式化 | 更改展示格式 |
| `print_report()` | 中文摘要和 JSON 输出 | 增加展示字段 |
| `show_error()` | 处理流程级错误，避免打印敏感响应 | 增加可理解的错误提示 |

最短阅读路径是 `arguments → main → query → daily_records → print_report`。请求签名和认证细节在第三方 SDK 内，本项目没有重新实现密码登录或加密算法。

## 11. 如何扩展一个日报指标

先确认云端日报确实有该 `key`，且它属于日报而非原始事件数据。再进行三个修改：

1. 在 `query()` 的指标列表中加入 key。
2. 在 `print_report()` 的标签与格式化逻辑中加入字段；保持 JSON 的原始信息可见。
3. 对照真实返回值确认单位、空值和时间字段，然后补充本文的字段表。

不要只加一个 key 就宣称“已支持”。测试账号无记录时，只能确认调用没有报错；不能证明解析了有数据情况下的所有字段。运动记录、体重事件、分钟级曲线还需各自的端点、分页和去重逻辑，不能直接当成现有日报列表的一项。

如果未来增加自动翻页，应验证游标字段、分页方向、重复页、重复记录、停止条件和最大页数；不应仅在 `has_more` 时无条件循环。

## 12. 排错步骤

1. **先区分登录与查询**：token 已保存但查询失败时先重试查询，不要立刻要求用户重登。
2. **检查解释器**：`python --version`，再用同一个解释器检查 `python -m pip show mi-fitness`。
3. **检查 token 路径**：登录和查询必须指向同一文件；只检查路径和权限，不打印文件内容。
4. **检查时间与同步**：明确日期、账号、App 最近一次同步；旧数据不等于接口失败。
5. **看结构化错误**：`--json` 中区分 HTTP `status_code` 和业务 `code`。
6. **404**：检查路径全名，尤其不要使用 `/app/v1/data/get_aggregated_data` 这样的仅替前缀路径。
7. **业务码 -8**：参数不被服务端接受；不要把错误返回转成“空数据”。本人最新快照在本次实测中尚未打通。
8. **网络超时**：检查 DNS、代理和网络；脚本只修正本进程 `NO_PROXY/no_proxy` 中的 `[::1]`，不会关闭代理或改系统配置。
9. **某一指标空**：比较更早日期和 App 页面；不应改成数值 0 来掩盖无数据。
10. **分页未完成**：缩小窗口，或明确开发并验证分页逻辑。

公开 issue 中可以提供 Python/SDK 版本、命令结构、日期范围、错误类型和业务码。token、二维码票据、账号标识和完整健康返回值不应作为普通故障日志上传。

## 13. 验证方法与实测范围

不需要账号的测试：

```bash
python -m unittest discover -s tests -v
python xiaomi_health.py --help
```

离线测试验证北京时间边界、越界数据过滤、未来窗口不访问网络、分页未完成明确报错。它们不会登录小米或读取真实健康数据。

真实账号回归按这个顺序做：扫码登录 → `latest` → 查询一个已知有步数的历史日期 → 对照手机 App 的日期与数值 → 检查无数据指标语义 → 确认凭据文件权限为 600。

2026-10-12 实测通过扫码登录、本人步数日报、近 7 天最新日报、指定日期连续三天历史查询。近期其他三个指标返回空，另一次只读接口检查可见更早睡眠日报。个人健康数值和登录材料不收录进公开仓库。

当前没有承诺所有手环型号、所有地区节点、全量历史、分钟级曲线或运动记录兼容性；这些需要单独测试。青龙使用同一个脚本，具体容器仍需满足 Python、网络和持久化目录条件，本次没有在用户的青龙服务器上部署。

## 14. 原教程与当前实现的关系

原教程存档在[原始开发手册](原始开发手册.md)。主要修正为：Python 版本要求为 3.11+；本人端点不只换前缀；综合摘要不等于步数对象；SDK 有自动刷新；当前用日报替代未打通的最新快照。

原文的 Nightscout 链路、SQLite、定时任务及其经验性结论没有在本项目实现或验证。开发和使用本仓库时，以本文的实测范围和实际源码为准。
